### Реестр обнаруженных отклонений

**F02-01 — двойной пробел → точка.** Воспроизводится при быстром вводе двух пробелов; при паузе может не проявляться. Для Markdown это существенный дефект буквального ввода (два пробела перед переводом строки обозначают hard line break). Источник проблемы предположительно связан с системной функцией; конкретное исправление не исследовалось. **Не устранять в PoC-02.**

**F03-01 — чрезмерное объединение Undo.** Возможное направление дальнейшей проверки — границы группировки, включая `breakUndoCoalescing()`; не считать это подтверждённым исправлением. **Не устранять в PoC-02.**

**F04-01 — недостаточная отзывчивость на одной мегабайтной строке.** Воспроизведено пользователем и подкреплено `Time Profiler`; остаётся приоритетной неопределённостью для TextKit 2. **Цель PoC-02 — проверить влияние переноса строк, а не автоматически объявить его причиной.**

### 5.5. Ограничение интерпретации

- Это наблюдения **всего процесса**, а не изолированное потребление памяти TextKit 2.
- Activity Monitor измеряет другое, чем `Persistent`/`Total Bytes` в Allocations; напрямую не сопоставлять значения и единицы МБ/MiB.
- Файлы 100 КБ / 1 МБ / 5 МБ открывались последовательно. Для сравнительного benchmark требуются **свежие процессы** и одинаковые условия, чего здесь не было.
- Краткие пики фиксировали визуально, не как точную кривую memory high-water mark.
- Memory Pressure при чистых сериях был зелёным; системное использование swap на скриншотах само по себе не относится к PoC01.

## 6. Instruments — Allocations

**Запись:** около **1 мин 6 сек**; пустой редактор → открыть `baseline-1000000-lf.md` → прокрутить → остановить запись.

| Показатель (`All Heap & Anonymous VM`) | Значение |
|---|---:|
| Persistent Bytes, на конец записи | **101,99 MiB** |
| Persistent heap | 62,21 MiB |
| Persistent anonymous VM | 39,78 MiB |
| Total Bytes (сумма всех зарегистрированных выделений, включая освобождённые) | **8,46 GiB** |
| Transient allocations | ~10,26 млн |
| VM: IOSurface, Total Bytes | ~5,56 GiB |
| VM: IOSurface, Persistent | ~10,45 MiB |

`Total Bytes` **не** означает одновременное потребление 8,46 GiB RAM. На графике после роста выделений наблюдалось относительное плато; короткая запись не проверяет долгосрочные утечки.

При выделении временного диапазона подъёма графика (~21–30 с) Statistics показал `Persistent` **79,40 MiB** и `Total Bytes` **4,59 GiB** *в контексте выбранного диапазона*. Эти числа **не следует автоматически считать чистым приростом RSS**. При анализе `Generations` на скриншоте выбранной Generation C показано ~48,84 МБ под стеком `start_dyld`, ~3,03 МБ под `start_wqthread`; это **места свёртки стеков, а не доказательство того, что функции сами являются владельцами памяти**. В Heaviest Stack видны Core Animation/Metal.

**Итог:** распределение и временные выделения зафиксированы, конкретная причина всплеска ~162 МБ через Allocations **не установлена**.

## 7. Instruments — Time Profiler

### 7.1. Стресс-файл `stress-1000000-no-newline.txt`

- В первой записи (~1:39) показано **36,46 с CPU-времени процесса**, из них **35,74 с Main Thread** (~98%); дорожка `Hangs` содержала зарегистрированный эпизод зависания.
- В повторной сохранённой записи `PoC01-TimeProfiler-LongLine.trace` пользователь раскрыл проблемный участок: выбранная выборка **3,41 с CPU**, из них ветка `_NSViewDrawRect` **2,96 с** (86,8%), а вложенная `hashProbe` — около **1,93 с** (56,5%). Значения — **inclusive CPU time**, не складывать по стеку.
- Путь исполнения на проблемном участке:

```text
NSView / NSTextViewportElementView.drawRect
  -> NSTextLayoutFragment.draw
  -> NSTextLineFragment.draw
  -> CTLineDrawWithAttributeOverrides / CTLine::DrawGlyphs...
  -> получение/перечисление атрибутов TextKit 2
  -> NSTextRunStorage / NSTextRange / NSCountableTextRange
  -> NSConcreteHashTable / hashProbe / rehashAround
```

**Подтверждено:** существенная нагрузка главного потока при отрисовке текста; TextKit 2/Core Text и операции диапазонов присутствуют в горячем стеке. **Не доказано:** что `hashProbe` — самостоятельная первопричина или что основная причина именно word wrap.

### 7.2. Обычный файл `baseline-1000000-lf.md`

- Контрольный профиль с аналогичной *общей последовательностью* действий: прокрутка → пауза → небольшой ввод/удаление → пауза → Undo/Redo.
- **8,74 с CPU-времени процесса**, **7,23 с Main Thread** (~82,8%). В дорожке `Hangs` — **No Data** для этой записи.
- Используются те же механизмы AppKit/TextKit 2/Core Text, однако длинный горячий участок с хеш-таблицами в показанных сводках выражен гораздо слабее (`hashProbe` около **37 мс за весь контрольный прогон**).

### 7.3. Сопоставимость и вывод

Длительности записей, точное число скролл-событий/клавиш, положение курсора и временные интервалы **не нормированы**. Числа **не являются точным ускорением в 4×** и не устанавливают задержку отдельного ввода в миллисекундах. В частности, ~1,93 с `hashProbe` в выделенном интервале стресс-записи и 37 мс в целом обычном прогоне не образуют строго сопоставимую метрику.

**Диагностический вывод:** сценарий одной строки заметно хуже по ручной отзывчивости и профилю CPU; структура документа — вероятный фактор. **Проверяемая гипотеза для PoC-02:** визуальный перенос длинной строки вызывает значительную часть этих затрат.

## 8. Ограничения достоверности и статус решения

### Что подтверждено

- F-01, базовая часть F-02/F-03, F-05/F-06/F-07; обычные файлы F-04 размером до 5 МБ.
- При выполненных проверках `fallbackCount=0` и активен TextKit 2.
- Исходные файлы сохранили SHA-256; **сохранение/перезапись реальных документов не проверялись**, поскольку приложение read-only.
- F04-01 воспроизводится как проблема пользовательской отзывчивости; есть профиль тяжёлой работы главного потока.

### Что не подтверждено / не проверено

- Влияние режима word wrap и сравнение TextKit 2/TextKit 1.
- Точные задержки пользовательских действий, «время до готовности», реальные показатели file I/O/decode/set-text из инструментализации.
- Выделенная «стоимость TextKit 2 в RAM», долгосрочные утечки, строгий независимый benchmark по размеру файла.
- Версия/сборка macOS и Xcode именно пользовательского измерения, питание, фиксированный размер окна и шрифт.
- Работа полноценного сохранения файлов, внешнего изменения, восстановления доступа, вкладок, подсветки Markdown.

### Разделение проблем

- **Продуктовый UX:** F02-01 (двойной пробел) и F03-01 (границы Undo). Исправление отложено.
- **Технический риск движка:** F04-01, патологически длинная строка; требуется узкая проверка причины.
- **Среда/методика:** фоновая нагрузка Xcode, колебания памяти, разные PID/фазы открытия, неполностью нормированные прогоны.
- **Codex:** в исходном `CHECKS.md` описаны ограничения среды запуска тестов и исправление теста pasteboard; пользовательский F04-01 нельзя автоматически считать ошибкой работы агента.

**Статус PoC-01:** функциональная приёмка завершена; технический вывод **частично подтверждён / условный (inconclusive для долгой строки)**. **Решение по движку:** сохранить TextKit 2 как ведущего кандидата, но **не утверждать окончательную архитектуру**, пока не проведён PoC-02. Следующее действие — узкое A/B сравнение word wrap ON/OFF в отдельном эксперименте, с тем же 1-МБ стресс-файлом и без исправления посторонних проблем.
